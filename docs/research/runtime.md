# Runtime research: Electrobun + WKWebView + PixiJS v8 (as of 2026-11-21)

## Verdict
1. CONDITIONAL GO on Electrobun + WKWebView + PixiJS v8 (WebGL renderer, not WebGPU) for macOS-first. Every capability you need exists in docs; nothing was run here, so prove it in a 1-day spike (below).
2. Risk 1: Electrobun is young and churning (v2.0.7 on 2026-11-20; 2.0 shipped 2026-08-21; 176 open issues). Real bugs touch your exact features: transparent/click-through (#263 open), first-click swallowed on non-key windows (#513), WKWebView blank when hidden (#566), webview not refitting on display change (#575).
3. Risk 2: Transparent + always-on-top + click-through floating window is the least-proven path. Docs give only `transparent` and `passthrough` (transparent regions only). Spike it before committing; fallback is bundleCEF (bigger) or a native shell.
4. Risk 3: WKWebView stops painting/rAF when the window is occluded or hidden (good for idle CPU, bad for "appear already painted" and for any capture). WebGPU in WKWebView needs macOS 26+; Electrobun floor is macOS 14, so ship WebGL2 as the default and treat WebGPU as opt-in.
5. Pixi v8.23.0 is solid for hundreds of sprites. Use imperative Pixi (autoStart:false, render on demand), not @pixi/react (v8.0.5, last release Dec 2025, bugfix-only).
6. Open-source friendly: Electrobun is MIT, PixiJS is MIT (PixiJS licence not re-fetched; widely known, unconfirmed here).

## Q1. Electrobun
- Version/cadence: npm `electrobun` = 2.0.7 (npm view). Stable releases: v2.0.4 2026-10-18, v2.0.5 10-26, v2.0.6 11-04, v2.0.7 11-20 (gh api repos/blackboardsh/electrobun/releases), plus many betas (beta.23/24 on 11-15). Roughly weekly to biweekly. Repo https://github.com/blackboardsh/electrobun: MIT, 13.1k stars, 176 open issues, pushed today.
- 2.0 (2026-08-21) moved the core into Zig, added Hutch CLI, Cottontail (experimental JSC runtime), experimental Warren UI, `<electrobun-webview>` and `<electrobun-wgpu>`. Bun stays the default main runtime. Author notes 1.x had only ~6 months of public life and asks for bug reports to stabilise 2.0. https://electrobun.dev/blog/electrobun-2-0/
- Platforms (https://docs.electrobun.dev/electrobun/guides/compatability/): macOS 14+ x64+arm64 on WKWebView; Windows x64/arm64 on WebView2; Linux x64/arm64 on WebKitGTK 4.1; CEF optional on all. README: macOS and Windows x64 and Ubuntu 24.04+ "Official", Windows ARM64 "Beta", other Linux community. https://github.com/blackboardsh/electrobun. Hutch cannot cross-compile; native CI per OS.
- CEF: yes, `bundleCEF: true` bundles and pins Chromium (larger files). Mixing renderers per window allowed on macOS/Windows, not Linux (third-party skill page only, unconfirmed). Gives a consistent WebGL/WebGPU engine on all platforms, at size cost.
- Windows (#): open issues include tray ID overflow (#610), tray idle memory growth (#571), update task truncation (#535). Linux: tray click events broken (#374). Not a concern for macOS-first but real if you promise cross-platform.
- Window features (https://docs.electrobun.dev/electrobun/apis/browser-window/):
  - `transparent` constructor option (bool). Docs say it works with native webview and CEF; floating-widget example uses `titleBarStyle:"hidden"` + `transparent:true` (WebSearch summary of the docs, unconfirmed on macOS by running).
  - `titleBarStyle`: "default" | "hidden" | "hiddenInset".
  - `setAlwaysOnTop(bool)`/`isAlwaysOnTop()` (method, not constructor option). `setFullScreen(bool)`/`isFullScreen()`. `setVisibleOnAllWorkspaces(bool)`.
  - `passthrough` constructor option: pointer input passes through transparent regions only. No whole-window click-through method. Open feature request #263 (fullscreen transparent + click-through) and #130 (kiosk mode).
  - Multiple windows: each `new BrowserWindow(...)`, `BrowserWindow.getById`. Extra `BrowserView`s supported.
  - Tray: documented under Main Process APIs (page list). Open macOS menu bug: submenu click closes menu (#581).
- RPC: typed, shared type file. Bun side `BrowserView.defineRPC<T>({maxRequestTime, handlers:{requests,messages}})` passed as `rpc` to `new BrowserWindow/BrowserView`; webview side `Electroview.defineRPC<T>(...)` then `new Electroview({rpc})`; calls `rpc.request.fn()` and `rpc.send.msg()`; Bun calls `webview.rpc.fn()`. Transport is a local WebSocket (issue #518 mentions "local RPC WebSocket transport", loopback). Official-doc page for RPC was not reachable; shape from WebSearch summary of blackboard.sh docs plus third-party skills (some outdated names). Unconfirmed exact current signatures: check docs.electrobun.dev. Sandboxed views (`sandbox:true`) disable RPC.
- Bundle size: README says "small self-extracting bundles" with zstd; no numbers anywhere I could fetch. Bun runtime shipped in app; discussion #599 on shrinking it. UNCONFIRMED: measure a hello-world build.
- Updates: BSDIFF binary patch updates, full compressed fallback, any static HTTPS host or managed hosting (README). Bugs: 2.0.6 update helper 100% CPU hang (#605, open), HTTP-only updates (#603), release-channel switching (#580), first-launch self-extraction rewrites app (#359, #540).
- Issues that would bite a Pixi scene app on macOS:
  - #566: hidden window shows blank frames on show(); WebKit does not paint WKWebView in an ordered-out or occluded window; private `_setWindowOcclusionDetectionEnabled:NO` unreachable from Electrobun.
  - #575: webview keeps old size after display or backing-scale change (affects canvas resolution moving between Retina and external monitors). Workaround: you own a resize listener; native fix proposed.
  - #513: non-key window swallows first mouseDown (drag regions and buttons need two clicks), directly hurts a floating window.
  - #263 click-through, #123 vibrancy missing.
  - macOS target 14.0 (#597).

## Q2. WKWebView graphics (Safari 26/27 era)
- WebGPU: shipped in Safari 26.0 on macOS/iOS/iPadOS/visionOS; WebKit says it "supersedes WebGL" and is preferred for new sites. https://webkit.org/blog/17333/webkit-features-in-safari-26-0/ . navigator.gpu needs macOS Tahoe (26)+ (https://bugs.webkit.org/show_bug.cgi?id=299237, per search summary). In WKWebView: Apple forum reply says Safari feature flags do not apply to WKWebView and WebGPU is on by default in WKWebView from iOS 26 (https://developer.apple.com/forums/thread/770862; single forum reply, not official docs). No flag needed on 26+, not available on macOS 14/15. Electrobun floor is 14, so a user on 14 or 15 gets WebGL only.
- WebGL2: available in WKWebView on macOS (long-standing). Gotchas: `powerPreference:high-performance` effectively a no-op and antialias:true reported to stop rendering in one bug (https://bugs.webkit.org/show_bug.cgi?id=290623-ish, per search; not verified which id); WebGL context loss on GPU/display switching (old WebKit bug, relevant to laptops moving between displays); Mac Catalyst WKWebView WebGL2 linkProgram failure on macOS 27.3 beta (https://developer.apple.com/forums/thread/855632; page unreadable, title only; Catalyst only, probably irrelevant). Handle `webglcontextlost`/`restored` (Pixi handles restore for WebGL). 
- Transparent canvas: needs `alpha:true`/backgroundAlpha:0 and the window `transparent`; premultipliedAlpha behaviour in WKWebView unconfirmed. Test.
- rAF/occlusion: WebKit treats occluded or ordered-out windows as hidden and stops producing frames (#566 body, source is a user report citing WebKit behaviour; also https://bugs.webkit.org/show_bug.cgi?id=331092 about occlusion detection, not rAF). Apple forum reports WebContent process sleeping when hidden with multi-second gaps (https://developer.apple.com/forums/thread/820860, summary only). No official Apple doc on exact rates: UNCONFIRMED. Consequence: a floating always-on-top window stays visible so keeps running; a fully covered or other-Space window pauses (free CPU saving). Show window before expecting first paint.
- OffscreenCanvas / workers: UNCONFIRMED in WKWebView. Safari has supported OffscreenCanvas 2D since 16.4 and WebGL in worker since 17, but I did not verify in a source. Pixi does not need a worker; keep main-thread.
- Power: no WKWebView-specific measurements found. Idle strategy must be yours: stop ticker, no timers (below). Verify with Activity Monitor / `powermetrics` on WebContent and GPU process.

## Q3. PixiJS v8
- Version: pixi.js 8.23.0 published 2026-11-11 (npm view; https://github.com/pixijs/pixijs/releases). Recent: 8.19 (June 2026), 8.17 (Mar), 8.16 added canvas renderer (Feb). Official AI "pixijs" skill exists (https://github.com/pixijs/pixijs-skills) and llms.txt/llms-full.txt at https://pixijs.com/llms.txt; use these in AGENTS.md.
- Renderers (https://pixijs.com/8.x/guides/components/renderers): WebGL "stable, widely supported" and recommended for production; WebGPU "feature-complete" but experimental/"still maturing", browser inconsistencies; Canvas experimental. Application `preference` defaults to webgl. Safari WebGPU caveats: `transientAttachment` false on some Safari, and a WebKit bug can lose the device with the transient bit on certain Safari 27.x. Use `preference:'webgl'`.
- Render on demand (https://pixijs.com/8.x/guides/components/application, /ticker): `await app.init({autoStart:false, ...})` and call `app.render()` yourself; or `app.ticker.stop()`/`start()`. Docs do not describe a render-on-demand mode or app.render() explicitly (confirmed absent); `app.render()` exists in the API (my knowledge, unconfirmed in fetched docs). Pattern: dirty flag; ticker runs only while any animation/tween is active; stop when queue empty; drive rendering from one rAF that cancels itself; no setInterval. Note `autoStart:false` does not stop an already running shared ticker; use a private ticker (sharedTicker default false).
- Perf (https://pixijs.com/8.x/guides/concepts/performance-tips): spritesheets; group by texture/blend mode to keep batches; sprites batch up to 16 textures; BitmapText for frequently changing text; culling is manual (`Culler`/`cullable`); use `ParticleContainer` with `Particle` for thousands of simple sprites (not Sprites).
- @pixi/react: v8.0.5 (2025-12-01), prior releases all bugfixes, alpha 8.1.0 with motion.dev support; peer `pixi.js ^8.2.6`, `react >=19` (npm view). Maintained but slow. JSX tags `<pixiSprite>` via `extend({Sprite})`. Declarative React is a poor fit for hundreds of per-frame-animated sprites (React reconciling per tick) and for render-on-demand; fine for a thin shell. Recommend: React owns state and HUD; an imperative Pixi scene controller subscribes to state and updates sprites.
- v7 to v8 traps (https://pixijs.com/8.x/guides/migrations/v8), for AGENTS.md:
  - Single `pixi.js` package; no `@pixi/*` imports. `await app.init({...})`; `new Application()` takes no options; `app.canvas` not `app.view`.
  - Graphics: `rect().fill()` / `circle().stroke()`; no `beginFill/endFill/drawRect/lineStyle`; holes via `cut()`.
  - `Assets.load` before `Texture.from(url)`; `Assets.add({alias, src})`; no `BaseTexture` (use `TextureSource`); `autoGenerateMipmaps`.
  - Ticker callback gets the Ticker: `ticker.add((t)=>t.deltaTime)`; use `t.deltaMS` for ms.
  - Constructors take option objects (`new Text({text, style})`, `BlurFilter({strength})`, `Mesh`, `BitmapText`); `Sprite.from` ok.
  - `DisplayObject` gone, `Container` is base; leaf nodes (Sprite, Graphics, Mesh) cannot have children; `container.name` -> `label`; `updateTransform` removed, use `onRender`.
  - ParticleContainer: `addParticle(new Particle(...))`, `particleChildren`, needs `boundsArea`.
  - Culling not automatic. `cacheAsBitmap` -> `cacheAsTexture()`. `eventMode` default is passive; set `'static'`/'dynamic' for interactivity. Event listeners via `on('pointerdown')`.
  - Filters: `pixi-filters` subpath imports (`pixi-filters/adjustment`); shaders use `Shader.from({gl, gpu, resources})`. Renamed: `NineSliceSprite`, `MeshSimple/Plane/Rope`. `settings` and `utils` removed. `getBounds()` returns Bounds (`.rectangle`). Interactive ancestors receive `globalpointermove` once per move since 8.23.0.
  - Always call `destroy()` with options on removed objects; textures GC automatically.
- Companions: pixi-filters 6.1.5 (npm, 2025-11-29, v8 OK); @pixi/ui 2.4.1 (2026-10-01); @pixi/layout 3.2.1 (2026-06-12, Yoga flexbox, v8); @pixi/spine for pixi v8 is `@esotericsoftware/spine-pixi-v8` (Spine's own; pixijs/spine repo stale since 2025-03 - check); particles: built-in ParticleContainer; old `@pixi/particle-emitter` 5.0.10 peers on pixi <8 (not v8-compatible), the `pixi-particle-emitter` npm name is unpublished; look for a v8 fork, unconfirmed. Tweening: GSAP 3.15.1 (free incl. plugins now) docs for PixiPlugin do not state v8 support (unconfirmed; GSAP can tween any property object so use it directly on sprites with its own ticker, `gsap.ticker` also feeds the idle-CPU problem, so wire `gsap.ticker.lagSmoothing`/`gsap.ticker.sleep` or drive it from your own loop); alternatives: motion (14.14.0), @tweenjs/tween.js 25.0.0. Text: BitmapText with `Assets.load` of fnt, or `SplitText` (8.16+); HTMLText has `safariFontDelay` option (8.23). Spritesheets: `Assets.load('sheet.json')`, TexturePacker format.

## Q4. Alternatives (one paragraph)
If WKWebView proves flaky, the cheapest pivot is the same Pixi code inside Electrobun with `bundleCEF` (consistent Chromium WebGL/WebGPU, larger download) or Tauri 2 (also WKWebView, so the same webview caveats, no gain). Electrobun's own experimental `bundleWGPU`/`<electrobun-wgpu>` native GPU surface sidesteps the webview but is experimental and would discard Pixi. For a dense but static-camera sprite scene, a Canvas2D renderer is a reasonable fallback only at low sprite counts; Pixi's canvas renderer is experimental. I would not switch renderer library: Pixi v8 is the mature option; Phaser or Excalibur add game-engine weight you do not need.
